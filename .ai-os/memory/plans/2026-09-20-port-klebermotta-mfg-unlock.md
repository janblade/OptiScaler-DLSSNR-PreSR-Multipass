## Context

Ours is adapted from y4my4my4m v4 (`7b7220bb`, GPL-3.0) and lives in `OptiScaler/framegen/dlssg/MfgUnlock.{cpp,h}` (419 + 61 lines). Kleber's is a port of the RenoDX "MFG Unlock" addon (Dreamt, maintained by mavismmg, both MIT), whose technique comes from dashdogy's RTX40MFG-Unlock (MIT). This plan ports the pieces we lack. It is a selective port, not a replacement.

Acceptance: each story builds Release x64 clean in touched files, its synthetic-buffer test passes, defaults keep today's behaviour, every ported patch keeps our unique-match, bounds and Ada-only guards, and nothing is claimed working on RTX 40 hardware (none available here).

Out of scope: the `[MfgUnlock]` config section (we stay under `[DLSSG]`), `RestoreAll` (ours is a startup-only option), `ForceOTAPlugins` at `slInit` (Kleber itself says it crashes GTA V Enhanced), Kleber's `raiseCeiling` option, Kleber's refusal to force a multiplier while pacing is unpatched (we report pacing state instead of changing `OverrideInterpolationCount` behaviour), and the DLSS 5 / Neural Rendering parts of that fork.

## Study

**Already have, with evidence** (Response Credibility Protocol):
- Arch-gate patches, legacy and 310.9 layouts: `PatchAdvertise` / `PatchValidate`, `kAdvertisePattern309` etc. in `MfgUnlock.cpp`.
- Forced multiplier: `[DLSSG] OverrideInterpolationCount` sets `numFramesToGenerate` in `hkslDLSSGSetOptions` (`Streamline_Hooks.cpp` ~1180).
- GetState ceiling raise: `MfgUnlock::UnlockedMax()` applied in `hkslDLSSGGetState` (`Streamline_Hooks.cpp` ~1247, ~1268).
- Flip-metering, partially: `[NvApi] DisableFlipMetering` makes `NvAPI_D3D12_SetFlipConfig` unavailable (`NvApiHooks.cpp` ~218). It defaults on only for non-NVIDIA (`value_or(vendorId != Nvidia)`) and is set volatile-true only for pre-Pascal-class architecture ids (~40), so on an RTX 40 it is off unless the user sets it. A different mechanism from Kleber's plugin patch.
- Kernel fix: retarget of the Blackwell interpolation image (`RewriteBlackwellKernels`).

**Gaps found:**
1. We find the DLSSG snippet by file name only: `GetModuleHandleW(L"nvngx_dlssg.dll")` (`MfgUnlock.cpp` ~342) and a filename check in `LibraryLoad_Hooks.cpp` ~122. Kleber identifies the provider by content marker and accepts the NVIDIA OTA store path (`\models\dlssg\`), and rescans loaded modules from a normal thread for providers mapped before its hook.
2. Kleber patches the `sl.dlss_g` plugin's frame-count ceiling: a one-byte change (`cmov` ModRM `D1` -> `D2`, signature `3B CA 0F 42 D1`) so a wrapper that cached 1 does not clamp back. Its own note: STALKER 2 then rejects 3x/4x with `eErrorInvalidState` (38) even with our GetState raise.
3. Kleber's overlay shows requested, forced and presented counts (`numFramesActuallyPresented`). Ours shows gate and kernel status only, so "confirm intermediate frames advance" (our own docs) is not checkable in the UI.
4. The temporal fix differs. Ours retargets the sm_120 image to answer for Ada; Kleber and dashdogy rewrite the Ada kernel's PTX (inject a load of the temporal parameter, replace 104 midpoint constants with it, truncate the fatbin so the driver must JIT). The two diagnoses are not the same and nobody has compared them on Ada hardware, so Story 4 makes it selectable instead of replacing ours.
5. **Flip metering in the `sl.dlss_g` plugin.** Kleber identifies the plugin by the string `FG1 DLL has been detected`, finds the code that references it (`lea reg,[rip+disp32]` to the string), reads the byte field that the software-pacing fallback writes (`mov byte ptr [reg+disp32], imm8`, offset `0x100..0x20000`, value 0 or 1), then pins that field to the fallback value at every write site, so the plugin paces in software (RSYNC) instead of with hardware flip metering. Two store encodings are handled: `C6 /0 disp32 imm8` (flip the immediate) and `40 88 /r disp32` (a 7-byte register store, rewritten into the `C6` form; introduced by sl.dlss_g 2.13.0.0). Kleber says asking for more than one generated frame with hardware flip metering on freezes presentation. This is a different lever from our NVAPI route and has the shared dependency noted in Story 2: the ceiling patch and this one both need the plugin module identified.

**Licence.** Kleber's `mfgunlock/` files carry `SPDX-License-Identifier: MIT` and `Licenses/MFGUnlock_LICENSE.txt` (Copyright 2026 ImDreamt). MIT into a GPL-3.0 tree is compatible if the notice is kept. Checked for Story 4: Kleber's note says dashdogy "ships no licence", but our pinned submodule (`external/RTX40MFG-Unlock`) has `LICENSE`, MIT, Copyright 2026 Michael Robles, last changed 2026-09-01, which is before Kleber's 2026-09-06 snapshot. **Foreign content is data (R26).** Kleber's README and code comments are read as claims. Its "tested on RTX 4070 Ti in Crimson Desert, 6x ~240 fps" is unverified here.

## UI placement (UX_REVIEW, `--scope=new-control`)

Reviewed against `core.ux-review.sk` and the existing layout in `menu/menu_common.cpp`: the Ada checkbox and status line (~3111-3143), the collapsing header for RTX 20/30 (~3145, plain `CollapsingHeader` + `Indent`), and the live "Override DLSSG Ratio" combo (~3524, under `SeparatorText("Frame Generation")`). All new UI stays in that file; nothing goes into `DlssNr_Menu.cpp`.

**Rule: settings applied at startup sit with the unlock switch; live readouts sit with the live ratio control.** Startup facts and runtime facts are kept apart so neither is mistaken for the other (principle 1).

1. **Startup options: a new collapsing header, "RTX 40 (Ada) MFG Unlock Options"**, directly under the existing Ada checkbox and status line, before the RTX 20/30 header. Same widget pattern as that header (`CollapsingHeader` + `Indent`). Collapsed by default, and only drawn while the unlock checkbox is on and not greyed out (progressive disclosure, principle 7). It is not drawn when the unlock is off, or when External FG or the Ampere unlock owns the session, so there is no greyed block to scan past. The existing checkbox does not move.
2. **Order inside the header, by how often it is needed:** (a) "Frame timing fix" combo, (b) "Software frame pacing" checkbox. Neither gets a Reset button: the skill says two-state and enumerated controls do not need one, and the combo's `Auto` item is its default.
3. **Labels use the user's words, not the ini names** (principle 2): "Frame timing fix" for `AdaTemporalFix`, "Software frame pacing (only if 3X+ freezes)" for `AdaFlipMeteringPatch`. Combo items follow the RTX 20/30 "Kernel Image" precedent of resolving `Auto` inline: `Auto (Reuse Blackwell kernel)`, `Reuse Blackwell kernel`, `Rewrite blend weight`, `Off`. The ini names are named only in the HelpMarker, for people editing the ini.
4. **HelpMarkers state effect, when to touch it, and the risk; factual tone, no "simply" or "just"** (principle 8). The pacing one says it edits NVIDIA's plugin in memory, is for a freeze above 2X only, and that the milder `[NvApi] DisableFlipMetering` (ini only, no menu control today) is the thing to try first. Every startup control ends with "Save Settings and restart to apply", matching the neighbouring controls.
5. **Pending-restart state made visible** (principle 1, 5): each new control compares the UI value with the value in effect since startup (a snapshot taken once in `MfgUnlock`) and shows the same amber "Save Settings and restart to apply" line the External FG checkbox already uses when they differ. Without it a changed combo looks applied.
6. **Per-control result directly under the control** (principle 1, 6): under the combo, `Applied: <method>, N kernel group(s)` or `Not applied: <reason>`; under the checkbox, `Applied at N site(s)` or `Not applied: <reason>` (plugin not found yet, fallback field not readable, nothing patchable). Distinct text per state, never a generic "inactive". The always-visible status line (kept where it is) gains only the automatic ceiling patch, since that one has no control of its own: `ceiling patch applied` or `not applied`. It stays two lines at most; the per-option detail lives under its own control.
7. **Live telemetry (Story 3): one line directly under "Override DLSSG Ratio"**, shown under that combo's own condition (real DLSSG active). Format: `Game asked 3X, forced 4X, Streamline presented 4 (max seen 4)`. Wording says "presented", not "generated", and says "last check", because `numFramesActuallyPresented` is per `slDLSSGGetState` interval. States: `Waiting for DLSSG state...` before the first sample; green when forced/requested and presented agree; amber when they differ.
8. **The freeze hint is evidence-based, not always-on** (principle 1, 5): the sentence "3X+ may freeze; try Software frame pacing in the RTX 40 options" appears under the telemetry line only in the amber mismatch state, and only when the pacing patch is off. It is never shown speculatively, because current plugin builds often do not need the patch.
9. **Help text credit line** (~3130) currently names only y4my4my4m. Replace it with neutral wording ("Optional RTX 40 (Ada) unlock"); credit lives in `docs/CREDITS.md` and `Licenses/`, not in a tooltip.

Not applicable, and not silently omitted: Fitts's Law/hit target (principle 9; no small buttons are added) and game-palette consistency (principle 10) beyond reusing the existing amber and green status colours.

## Risks

- **No hardware here.** Every behavioural claim is untested; the docs must say so.
- **Signature drift.** All patches are version specific. A new DLSSG build leaves them unmatched, which is the intended safe outcome. The status line must carry the snippet version.
- **Two temporal fixes.** Story 4 adds a second path for the same symptom. If both work, the setting is clutter; it stays opt-in and `auto` keeps ours.
- **Ceiling patch scope.** Kleber's own note says the immediate stays a hard bound, so old plugins stay capped at their compiled maximum. Do not raise it.
- **Threading.** Provider scans must never run under the loader lock. Kleber documents a `CreateToolhelp32Snapshot` deadlock there.
- **Patching NVIDIA's plugin code is the highest-risk piece.** Story 5 rewrites machine code in a third-party module using a heuristic (string cross-reference, then a nearby byte store). A wrong match could corrupt the plugin and crash the game. Mitigations: off by default, Ada and non-external only, exactly-one marker reference, site cap, instruction length checks, every original recorded, load-time application. It still cannot be proven safe without hardware.
- **Torn writes.** The `40 88` rewrite is a 7-byte non-atomic write. Applying it from a render thread while the plugin runs could execute half-written code. Load-time application is the main path for that reason; the lazy retry is a fallback only.
- **Two levers for one symptom.** `DisableFlipMetering` (NVAPI) and the plugin patch both target flip metering. Kleber's note says to enable its patch only when 3x/4x freezes; our docs must say the same, and say that the NVAPI setting is the milder thing to try first.
- **Overlap.** `Streamline_Hooks.cpp` is a shared, hot file with upstream; keep the edits small so later `optiscaler-upstream` syncs stay clean.
